# V4 重构假设说明

本文按考试要求第六章模块十一的 12 项内容逐条说明。容量与性能数字以当前考试环境和 2026-08-06 的生产压测为依据，不外推为长期生产 SLA。

## 1. 为什么选择异步事件驱动

V2 在一次 HTTP 请求内完成文件上传、解析、校验和逐行写库。文件变大后，请求会同时受到 Vercel 请求体、函数时长、内存和客户端连接稳定性的限制，失败后也难以判断已经处理到哪一行。V4 让浏览器把文件直传私有 Blob，任务 API 只在 PostgreSQL 事务中创建 `import_tasks` 和文件准备 Outbox，立即返回 `task_id`；准备 Worker 解析一次文件并生成分片，批次 Worker 再异步处理。这样可以独立重试、查询进度和定位故障。

同步方式仍适合小文件、低并发、处理时间可稳定控制在数百毫秒且调用方必须立即取得完整结果的场景。此时异步队列反而增加状态管理和最终一致性成本。

## 2. 处理单元大小

默认批次为 500 行，10,000 行形成 1 个文件准备消息和 20 个批次消息。每条批次消息只带 `outboxId`，数据放在对应的私有 Blob 分片中。500 行可以把 SKU 查询和运单写入合并为少量批量 SQL，同时把单次失败的重试范围、函数内存和事务时长控制在较小范围。

批次过大会增加单次函数超时、数据库锁占用、内存峰值和重试成本；批次过小会放大 QStash 请求数、Outbox 行数、数据库往返及状态聚合开销。该值是考试数据下的起点，应根据真实行宽、错误率和数据库规格重新压测。

## 3. Worker / Consumer 容量规划

生产环境使用 QStash 调用无状态 Vercel Route Handler，横向容量由 QStash 投递速率、Vercel 函数并发和数据库可用连接共同限制。Worker 不保存本地状态，同一批次可由任意实例处理。当前没有在代码中宣称固定的生产并发上限；免费计划由平台管理并发，监控页以队列积压、批次 P95 和数据库错误作为扩缩容信号。

容量规划先按每批 500 行估算消息数量，再逐步提高队列并发，直到数据库连接等待或写入延迟明显上升。长期生产应为文件准备与批次消费使用独立队列和并发上限，避免大文件解析占满批次处理容量。

## 4. 10,000 单/分钟性能推导

10,000 行按 500 行/批为 20 批。2026-08-06 生产实测中，20 批总耗时 P50 为 260 ms、P95 为 457 ms，任务从创建到完成为 5,929 ms，成功 9,989 行、失败 11 行。因此该次任务的实际吞吐约为 `10000 / 5.929 * 60 = 101,197 行/分钟`，接口返回的计量值为 101,086 行/分钟，达到 10,000 行 60 秒内完成的目标。

该结果是一次考试环境实测，不代表长期 SLA。若按保守的每批 1 秒、有效并发 4 估算，20 批约需 5 轮，即批次阶段约 5 秒，再加文件准备和投递开销，仍应低于 60 秒。最终以多轮压测分位数为准。

## 5. 数据库连接池和 Worker 并发

Vercel 运行时通过 `POSTGRES_PRISMA_URL` 使用 Neon pooled connection，迁移和直连操作使用 `POSTGRES_URL_NON_POOLING`。每个 Worker 复用进程内 Prisma 单例，避免每次请求创建新客户端；单批使用一次 SKU `IN` 查询、一次历史外部编码查询和批量事务写入，减少连接占用时间。

Worker 并发不能无限提高，必须低于数据库连接池可承受范围。当前考试部署采用平台默认投递并发，没有配置或声称一个未经验证的固定值。生产化时应结合 Neon 连接指标设置 QStash 队列并发，并在连接等待、数据库 P95 或 5xx 上升时限流。当前报告尚未采集峰值数据库连接数，这是容量证据的已知缺口。

## 6. Outbox 如何避免消息丢失

任务记录与文件准备 Outbox 在同一个 PostgreSQL 事务中提交：事务成功时两者同时存在，事务失败时两者都不存在。因此不会出现“任务创建成功但没有可投递事件”的中间状态。Dispatcher 只有在 QStash 接受消息后才把 Outbox 标为 `SENT`；发送失败时记录原因、增加 `retry_count` 并按 `next_retry_at` 退避重试。上传请求结束后的投递、任务轮询补投递和 Vercel Cron 恢复扫描共同负责唤醒未发送事件。

## 7. Job 幂等

QStash 使用 Outbox ID 作为消息去重 ID，但系统不依赖消息只投递一次。批次从 `PENDING/RETRY` 条件更新为 `PROCESSING`，只有领取成功的 Worker 才执行；已完成批次重复消费会直接返回。运单以 `task_id + batch_index + row_number` 形成唯一 `dedupeKey`，`createMany(skipDuplicates)` 阻止重复落库；任务进度只在批次首次从处理中完成时累计。超时锁为异常中断后的重新领取提供基础恢复能力。

## 8. 部分失败策略

业务允许同一文件中的合法行先落库，非法行写入 `import_task_errors`，任务最终标记为 `PARTIAL_SUCCESS`。原因是 SKU 不存在、数量错误等通常是行级问题，整体回滚会重复处理大量合法数据并放大重试成本。错误记录包含行号、字段、错误码、修复建议和 Trace，便于修复后重新导入；唯一键负责避免已成功行重复写入。

如果未来出现“整份文件必须原子生效”的业务规则，则不能复用本假设，需要引入暂存表、整单校验和发布事务。

## 9. SKU 校验降级

仅当 SKU 主数据查询发生数据库或依赖异常时进入降级，而“SKU 不存在”属于正常校验失败，不触发降级。降级后仍执行格式、必填和数量校验，任务写入 `degraded=true`，Trace 和任务页显示风险提示；未经过 SKU 主数据校验的行不能被静默当作完整校验结果。

服务恢复后，新任务自动走正常校验。当前考试实现不自动回溯补校验历史降级任务，长期生产需由产品确认是否增加补偿扫描、暂存而不正式入库，或阻断全部写入。默认更保守的生产建议是依赖不可用时暂停批次重试。

## 10. 敏感数据脱敏

手机号和地址在错误表中只保留脱敏值，Trace 不记录完整订单载荷，QStash 消息只包含 Outbox ID。服务端密钥来自环境变量，不进入浏览器包和源码。排障人员通过 task、batch、row、error_code 和 trace_id 定位问题，不依赖完整敏感原文。真实生产还应增加日志访问权限、审计、加密和保留周期。

## 11. 压测数据生成与清理

`npm run seed:data` 批量重建 20,000 条 `sku_master`，并生成 10,000 行 `test-data/10000-orders.xlsx`；文件固定包含少量非法 SKU，用于验证部分成功和 E001 错误链路。`SEED_SKU_COUNT`、`SEED_ORDER_COUNT`、`SEED_ORDER_PREFIX` 可调整规模和重复导入前缀，`GENERATE_FILE_ONLY=1` 可只生成文件。

脚本会清理并重建 SKU 压测主数据。任务、错误、性能、Trace、Outbox、运单和 Blob 原文件属于业务/审计数据，不在通用 seed 命令中无条件删除，避免误删；考试结束后应在明确目标环境中按任务前缀或 task_id 清理，并删除临时 Blob、QStash 集成和测试数据库。

## 12. 待产品和运维确认的问题

- 同一文件重复上传的去重窗口，以及成功行修复重跑的业务语义是什么？
- SKU 服务不可用时应暂停、暂存还是允许降级入库，降级任务是否必须补校验？
- 文件、错误明细、Trace、Outbox 和运单分别保留多久，谁有权限查看敏感字段？
- 峰值文件大小、日任务量、租户隔离、目标 SLA 和允许的最大队列积压是多少？
- Neon、Vercel、QStash 的付费容量和告警渠道由谁负责，数据库连接数上限是多少？
- 解析规则变更如何审批、版本化和回滚，AI 生成规则导致批量错误时由谁确认止损？

## 已知边界

本考试项目使用免费额度完成短期部署与验收。相同文件当前允许再次创建任务，生产环境可在产品确认后增加文件哈希时间窗去重。事件信封使用 `schema_version`，新增字段保持可选，消费者忽略未知字段；语义不兼容时升级版本。原文件和解析分片存入私有 Vercel Blob，本地未配置 Blob/QStash 时分别回退到本地文件系统和数据库任务队列。
