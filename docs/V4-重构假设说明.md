# V4 重构假设说明

## 架构选择

上传请求保存文件，创建 `import_tasks`、批次和 `event_outbox` 后立即返回 `task_id`。Dispatcher 从 Outbox 领取批次事件，生产环境投递到 Upstash QStash；QStash 调用带签名校验的 Vercel Worker Route Handler。本地未配置 QStash 时使用数据库任务队列回退。该选择避免在 Vercel 上维护常驻 Redis Worker，同时保留真实的消息投递、重试和失败记录。

## 处理单元与容量

默认每批 500 行，10,000 行使用 1 个文件准备消息和约 20 个批次消息。每条消息只携带 `outboxId`，不携带文件或行数据。文件准备 Worker 只解析一次并写出分片快照；每个批次只读取自己的分片，执行一次 SKU `IN` 批量查询、一次 `createMany(skipDuplicates)` 批量写入和一次进度聚合。理论吞吐由 QStash/Vercel 并发和单批阶段耗时共同决定，最终以部署环境压测日志为准；免费计划并发限制属于已知容量边界。

## 可靠性与幂等

任务、批次和 Outbox 在同一事务中提交，Dispatcher 投递失败会递增 `retry_count` 并按退避时间重试。QStash 使用 Outbox ID 作为消息去重 ID，并对非 2xx Worker 响应重试。批次状态从 `PENDING/RETRY` 原子领取到 `PROCESSING`，超时锁允许恢复；已完成批次重复消费会快速返回。运单使用 `task_id + batch_index + row_number` 作为唯一 `dedupeKey`，批量写入跳过重复键；进度只在批次从 `PROCESSING` 首次完成时累计。

相同文件允许再次创建任务，便于修复数据后重跑；历史 `externalCode` 批量校验和任务内 `dedupeKey` 共同防止重复运单落库。生产环境可在产品确认后增加文件哈希时间窗去重。

## 部分失败、降级与安全

校验错误按行写入 `import_task_errors`，成功行继续批量入库，任务最终为 `PARTIAL_SUCCESS`。SKU 主数据查询异常时进入 `degraded` 模式，保留格式/必填校验并在任务页提示风险。手机号和地址在错误表中只保留脱敏值。QStash Worker 使用当前/下一签名密钥验证请求，私有 Blob 只由服务端凭据读取。

## 文件与恢复策略

生产原文件和解析快照存入私有 Vercel Blob，数据库只保存可复读 URL；本地保存在 `.data/imports`。上传后的 `after()` 立即触发 Outbox 投递，任务轮询也会补充投递；Vercel Hobby 每日 Cron 作为最低频的灾难恢复扫描。QStash 自身负责已接收消息的重试和失败日志。

## 清理和事件演进

考试演示后可删除 Blob Store、QStash 集成和压测数据。生产环境按保留周期归档 `event_outbox`、错误和性能日志；压测数据可通过 `seed:data` 重建。事件统一使用 `schema_version`，新增字段保持可选，语义变化升级版本；消费者忽略未知字段。

## 待产品/运维确认

长期生产前需要确认 Blob 保留周期、QStash 付费容量、Vercel Function 并发上限、SKU 主数据刷新频率、重复文件去重窗口和告警渠道。本考试项目使用免费额度完成短期部署和验收。
