# V4 重构假设说明

## 架构选择

上传请求只负责保存文件、创建 `import_tasks`、创建批次和写入 `event_outbox`，事务提交后立即返回 `task_id`。Dispatcher 从 Outbox 领取批次事件；生产环境投递到 BullMQ/Redis，由 `worker:start` 常驻消费者处理，本地未配置 Redis 时使用数据库任务队列直接消费。

## 处理单元与容量

默认每批 500 行，4 个批次并发。每个批次只进行一次规则引擎解析、一次 SKU `IN` 批量查询、一次 `createMany(skipDuplicates)` 批量写入和一次进度聚合。10,000 行约 20 批，Worker 并发 4；当单批平均 2 秒时理论吞吐约 60,000 行/分钟，数据库连接峰值控制在 Worker 并发以内，实际以压测日志为准。

## 可靠性与幂等

任务、批次和 Outbox 在同一事务中提交，Dispatcher 投递失败会递增 `retry_count` 并按退避时间重试。批次状态从 `PENDING/RETRY` 原子领取到 `PROCESSING`，重复消息无法再次领取。运单使用 `task_id + batch_index + row_number` 作为唯一 `dedupeKey`，批量写入跳过重复键；进度只在批次从 PROCESSING 首次完成时累计。

相同文件允许再次创建任务，便于修复数据后重跑；历史 `externalCode` 批量校验和任务内 `dedupeKey` 共同防止重复运单落库。生产环境可在产品确认后增加文件哈希时间窗去重。

## 部分失败、降级与安全

校验错误按行写入 `import_task_errors`，成功行继续批量入库，任务最终为 `PARTIAL_SUCCESS`。SKU 主数据查询异常时进入 `degraded` 模式，保留格式/必填校验并在任务页提示风险。手机号和地址在错误表中只保留脱敏值。

## 清理和事件演进

生产环境按保留周期归档 `event_outbox`、错误和性能日志，索引使用状态/时间字段；压测数据可通过 `seed:data` 重建 SKU 主数据和测试文件。事件统一使用 `schema_version`，新增字段保持可选，语义变化升级版本；消费者忽略未知字段。

## 待产品/运维确认

需要确认对象存储、Redis/队列托管、Worker 并发上限、SKU 主数据刷新频率、错误明细保留周期、重复文件去重窗口和告警渠道。
