# V4 反思题

## 1. 为什么不能继续同步阻塞，什么时候同步更合适

V2 把上传、解析、SKU 校验和逐行写库放在同一个 HTTP 请求中。10,000 行和大文件会占用函数时间、内存、数据库连接和客户端连接，任一环节抖动都会导致整体超时；请求失败后还难以判断哪些行已经写入。异步任务把接收请求与执行解耦，可以分片、重试、查询进度并记录完整 Trace。

当数据量小、处理稳定在数百毫秒、失败必须整体返回、没有后台状态管理需求时，同步更简单可靠。例如单条订单创建或几十行以内的即时校验，同步事务减少了队列、轮询和最终一致性的复杂度。

## 2. 处理单元变大或变小的影响

处理单元变大可以减少消息数、状态行和数据库往返，批量 SQL 的效率也更高；代价是单次内存、事务时间、锁占用和失败重试范围变大，更容易触发函数超时。处理单元变小会提高并行度、缩小重试范围并让进度更细，但会增加 QStash 调用、Outbox、数据库往返和聚合开销。当前选择 500 行，是在 10,000 行考试数据上的压测折中，而不是对所有文件固定不变的真理。

## 3. 吞吐提升到 50,000 单/分钟时的瓶颈和扩展

在当前实现中，最可能先遇到的是数据库写入和连接池，而不是 Redis/QStash 消息传递。Worker 可以无状态横向扩展，队列也能提高投递并发，但所有 Worker 最终都竞争同一个 PostgreSQL 的连接、索引维护和写入 I/O；盲目增加并发会让数据库延迟和 5xx 更严重。

扩展顺序是先用监控确认阶段耗时与连接等待，再减少每批 SQL 次数、保持批量写入并优化唯一索引；随后给 QStash 队列设置与数据库容量匹配的并发上限，并水平扩展 Worker。若数据库仍是瓶颈，可按租户或业务键分区、使用写入暂存表后合并，或升级数据库规格。文件准备应使用独立队列，避免大文件解析占用批次消费容量。

## 4. 为什么业务幂等比消息只投递一次更重要

分布式链路无法廉价地保证绝对“只投递一次”。Worker 可能已经提交数据库事务，却在返回 2xx 前断线，队列只看到超时并再次投递；网络重试、进程重启也会产生相同情况。队列去重只能降低重复概率，不能证明业务副作用没有重复发生。

业务幂等把正确性放在最终写入侧：批次条件领取、完成状态判断、运单唯一 `dedupeKey` 和 `createMany(skipDuplicates)` 共同保证同一消息执行多次仍只产生一次业务结果。因此可以接受队列的至少一次投递语义。

## 5. 部分行失败时整体回滚还是成功行先入库

本题场景选择成功行先入库。SKU 不存在、数量错误通常只影响个别行，整体回滚会让大量合法行重复等待和重跑，也会放大大文件的事务时间。错误行记录行号、字段、错误码、修复建议和 Trace，任务标记 `PARTIAL_SUCCESS`，用户修复后可以重传；幂等键避免成功行重复。

但这取决于业务原子性。如果一份文件代表不可拆分的结算批次或库存调拨单，部分成功会破坏业务约束，就应先写暂存表，全部校验通过后一次发布，而不是沿用当前策略。

## 6. 原始值排障与敏感数据保护

错误记录应遵循最小必要原则。SKU、数量等非敏感字段可保留原值；手机号只保留部分前后缀，地址只保留足以判断格式或区域的片段，Trace 不记录完整订单载荷。排障主要依靠 task、batch、row、field、error_code 和 trace_id 关联，确需查看原文时通过受权限控制的原文件访问，而不是把敏感信息复制到所有日志系统。

生产环境还应配置字段级加密、访问审计、角色权限和自动过期，并确保 QStash 消息只带内部 ID。这样既保留定位能力，也降低日志泄露的影响范围。

## 7. Outbox 千万级后的清理、归档和索引

在线表只保留未发送、待重试及近期记录。已发送并超过审计周期的数据按时间分区批量归档到低成本存储，再小批量删除，避免一次大事务造成锁和膨胀；失败和死信记录保留更久。清理任务必须可重入，并记录归档水位和校验数量。

投递扫描使用 `(status, next_retry_at)` 组合索引，并只覆盖可投递状态；按聚合查询使用 `aggregate_id` 索引，时间归档使用 `created_at`。大表可按月分区，使删除旧数据变成分区淘汰。已经发送的海量数据不应长期参与热索引，也不应把大 payload 放进索引。

## 8. 如何快速发现 AI 解析规则问题

规则问题通常表现为同一 `rule_id/rule_version` 切换后，多任务同时出现字段必填错误、SKU 不存在、数量格式错误或特定列为空，而数据库问题更常表现为查询/连接异常、5xx、批次重试和多个规则共同受影响。

监控应按规则版本聚合成功率、错误码、空字段比例、SKU 命中率和每批解析行数，并与部署版本和历史基线对比。Trace 记录规则选择、解析开始/完成、解析行数和校验阶段；若解析完成但 E001/E002 在某个规则版本突增，可迅速定位为映射问题。发布规则前还应使用样本试解析和人工确认，异常时暂停该规则、回滚到上一版本，而不是继续扩大错误数据。
